# 2026-09-26 同机基准（5A）：Compat / Vips、真实照片、实况照片、三浏览器

源码版本 `528b7b8`（0.17.0 工作版本，未部署）。这是一份独立的新基准，不与旧的 Linux/Intel 历史基线或其它主机的数字换算提速比例。原始 JSON、输出文件和临时测试页只保存在临时目录中，不入库。

## 环境与方法

- 主机：Intel Core Ultra 7 255H，WSL2 内 8 个逻辑 CPU、12 GiB 内存，内核 6.18.33.2-microsoft-standard-WSL2（Debian）。
- 浏览器：Playwright 1.58.2 自带的 Chromium 145.0.7632.6、Firefox 146.0.1、WebKit 26.0，均为无头模式，页面处于跨源隔离状态（开发服务器发送 COOP/COEP）。
- 合成用例：`PICFORGE_BENCH_LAYER=engine` 下的 `S01–S06`（T00 harness，合成画面，不代表画质）。每项取 1 次首次样本和 3 次热样本。
- 真实照片：直接调用生产 `createImageProcessor`（Compat）和实验 Vips 引擎。同样取首次样本加 3 次热样本，下表记录热样本中位数。

  | 编号 | 内容                                                                | 尺寸      | SHA-256 前 16 位                        |
  | ---- | ------------------------------------------------------------------- | --------- | --------------------------------------- |
  | R1   | 已批准的安卓动态照片 JPEG（P3 ICC，附带 Ultra HDR/多图数据）        | 3072×4096 | `8195cbc1d9b465c1`                      |
  | R2   | 由已批准 HEIC 用 ImageMagick 转出的 q95 JPEG（保留 P3 ICC）         | 4284×5712 | `bd2c78653670ef4f`                      |

- 画质：用 ImageMagick 7 将源图转为 sRGB，再用 Lanczos 缩放到输出尺寸作为参考图，计算 SSIM（越接近 1 越好）和 PSNR。这个参考图天然偏向同样使用 Lanczos 的 Vips，比较两种引擎时应主要看"同体积下的画质"。
- 主线程长任务（Long Tasks）只有 Chromium 支持统计。

## 画质与体积（R2 24MP → 1920，Chromium）

| 格式 | 质量                   | Compat 体积 · SSIM                                                                 | Vips 体积 · SSIM                                                                   |
| ---- | ---------------------- | ---------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------- |
| JPEG | 60 / 70 / 75 / 90      | 138 KB · 0.935 / 167 KB · 0.944 / 190 KB · 0.949 / 427 KB · 0.969                  | 166 KB · 0.943 / 199 KB · 0.951 / 224 KB · 0.956 / 500 KB · 0.975                  |
| WebP | 60 / 70 / 75 / 80 / 90 | 116 KB · 0.946 / 132 KB · 0.950 / 140 KB · 0.952 / 173 KB · 0.958 / 300 KB · 0.970 | 124 KB · 0.951 / 140 KB · 0.954 / 149 KB · 0.957 / 184 KB · 0.963 / 319 KB · 0.976 |
| AVIF | 40 / 50 / 60 / 70      | 52 KB · 0.934 / 77 KB · 0.948 / 117 KB · 0.959 / 154 KB · 0.965                    | —                                                                                  |

- 同样体积下，JPEG 两种引擎画质相当（约 166 KB 时均为 0.943–0.944）；WebP 上 Vips 略好（约 124 KB 时 0.951 对 0.946）。Vips 的锐利缩放会带来更多细节和更大的文件。
- AVIF 效率最高：q50 为 77 KB · 0.948，而 WebP 要约 132 KB 才能达到同等 SSIM，体积约小 40%。代价是编码更慢（Chromium 约 2.5–4 s，Firefox 约 23–36 s）。
- 实况照片导出的 JPEG 与 LittleCMS 的 P3 → sRGB 参考图相比 SSIM 为 0.974，三种浏览器的字节完全一致，说明颜色转换正确。

## 跨浏览器一致性

Compat 缩图使用各浏览器自己的 Canvas 缩放（`imageSmoothingQuality = 'high'`），同样设置在不同浏览器得到不同的像素：

- R2 → 1920 WebP q75：Chromium 140 KB，Firefox 160 KB，WebKit 172 KB。PSNR 分别为 37.1 / 34.9 / 35.9 dB。
- R1（拍摄屏幕、摩尔纹多）→ 1920 AVIF：Chromium 135 KB，Firefox 269 KB，WebKit 320 KB。

Firefox 和 WebKit 的缩放保留了更多混叠（锯齿/摩尔纹），文件更大，画质也不更好。Vips 输出在三个浏览器中逐字节一致。

## 结论

1. **Compat 仍应是生产默认引擎。** 缩放场景下 Compat 比 Vips 快 1.5–2.6 倍（批量约 3.5 倍），同体积画质相当。Vips 只在原尺寸 JPEG 重新编码时更快，而且没有主线程阻塞。
2. **最大的交互问题是 Compat 的主线程阻塞**：每张照片 0.15–0.5 s，批量时累计更长。把解码/缩放移入 Worker（OffscreenCanvas）可以直接消除。
3. **最大的画质问题是缩放依赖浏览器。** Firefox/WebKit 的混叠让文件变大、画质不稳定，需要统一的高质量缩放（例如分级缩小或 WASM 缩放），再用本基准验证三浏览器趋于一致。
4. **最大的速度瓶颈是实况照片的视频**：约占总时间的 70%，由单线程 WASM x264 造成。候选方案是 WebCodecs 硬件编码（保留 FFmpeg 回退），或多线程 FFmpeg（需要生产环境发送 COOP/COEP）。静态图 24MP 需 5–6 s，其中解码与编码的拆分尚待测量。
5. **Firefox 在本环境中所有 WASM 工作慢 2.5–10 倍。** 这与早先记录的 Firefox 实况照片约 77.6 s 一致，但仍需用真实桌面 Firefox 确认，不能直接当作用户体验的结论。
